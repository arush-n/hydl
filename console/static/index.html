    Connection and authentication notes

    Mode is not a server flag — no such switch exists. Client-facing binds 0.0.0.0, passes --allow-op so a connecting player can op themselves (which /npc requires — it is gated on hytale:WorldEditor), and turns on LAN discovery at boot. That last one matters: discovery is per-process and does not survive a restart, so a relaunched server silently vanishes from the client's Local list with no error anywhere. Headless binds loopback only. A launched server writes its universe under artifacts/console-hytale/, never into the install.

    Auth mode is the thing most likely to stop a real client joining, and the other two values fail differently. offline never gets off the ground — InitialPacketHandler (:209-227) requires Constants.SINGLEPLAYER and that the connecting UUID owns the world, disconnecting with offlineModeSingleplayerOnly / offlineModeOwnerOnly. insecure gets much further and still fails: the server completes its development flow all the way into setup:assets-request, then the client hangs up with “server requires development mode which is not supported in build”. So client-facing defaults to authenticated, which needs the server to hold its own tokens — run auth login device in the console above and complete the code prompt.

    Latched from the server's own log as it boots, not probed afterwards. The game port is QUIC over UDP, so it never appears in a netstat filter on LISTENING — that is a TCP state. Checking that way reports a healthy client-facing server as having no game port.

    
  
    

  
    
    
    Command limitations
    
          
    
    
    
    No console command can spawn an NPC, and no
      setting changes that. The interactive console runs commands as
      ConsoleSender.INSTANCE
      (ConsoleModule.java:113) and so does
      --boot-command (HytaleServer.java:447) — the
      same senderless identity. ConsoleSender.hasPermission()
      returns true unconditionally, so permission is not the
      blocker. But NPCSpawnCommand extends AbstractPlayerCommand,
      which fetches senderAsPlayerRef() and, when it is null,
      replies errors.playerOrArg and returns without executing
      (AbstractPlayerCommand.java:33-38). The NPC spawns at the
      sender's position, and the console has no body.
    
    
    The refusal message sends you down a dead end.
      It reads “Sender must be a player or provide the --player option!”,
      but that option does not exist on this command — passing it gets
      “Could not find an optional argument with the name … 'player'”.
      Both base classes share one translation string and only
      AbstractTargetPlayerCommand declares the argument. Measured
      against a live server, not inferred.
    
    
    So there are exactly two ways to get an agent NPC into a
      world: connect a real client and run /npc spawn <role>
      in chat, or let the bridge mod create the entity programmatically, which
      is what the RL system already does and why it never needed a client.
